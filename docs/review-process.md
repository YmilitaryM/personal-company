# 独立评审制度 v2.0 — 三轮辩论式评审

## 评审团构成

3名独立评审员，不隶属于任何项目组，直接向CTO报告评审结果。

### 评审员画像
- **R1**: 技术架构专家 — 侧重技术合理性、架构质量、安全性
- **R2**: 产品质量专家 — 侧重需求符合度、用户体验、完整性
- **R3**: 工程效率专家 — 侧重代码质量、TDD合规、可维护性、风险

### 独立性保障
- 评审员不参与任何项目的具体开发工作
- 评审员的评价不受CTO或项目组长影响
- Round 1 严格隔离：3人同时评审，互相不可见
- Round 2 交叉辩论：全部可见，互相挑战
- 投票结果公开透明

## 核心理念

**旧模式**: 3个专家各自在专业方向上打分 → 汇总 → 过/不过
**问题**: 质量完全取决于个体能力，没有跨专业视角的碰撞

**新模式**: 独立评审 → 交叉辩论 → 合议裁决
**质量机制**: 辩论 IS the quality mechanism — 通过不同视角的碰撞发现个体盲点

## 三轮评审流程

```
Round 1: 独立评审（并行隔离）
        │
    ┌───┴───┐
    ▼       ▼       ▼
   R1      R2      R3     ← 各自审查所有方面，独立打分
    │       │       │
    └───┬───┘       │
        ▼           │
   汇总 Round 1 结果  │
        │           │
        ▼           │
Round 2: 交叉辩论    │
    ┌───┴───┐       │
    ▼       ▼       ▼
   R1      R2      R3     ← 看到彼此结果，互相挑战
    │       │       │      ← 辩护/让步，识别冲突
    └───┬───┘       │
        ▼           │
   汇总辩论结果      │
        │           │
        ▼           ▼
Round 3: 合议裁决
        │
    ┌───┴───┐
    │ 共识/分歧 │          ← Orchestrator 综合
    │ 修订分数  │          ← 每个审查者的最终分数
    │ 最终裁决  │
    └───┬───┘
        ▼
   最终结果
```

## Round 1: 独立评审（并行隔离）

### 原则
- 3名评审员同时启动，完全隔离
- 每个评审员审查 **所有方面**（不只自己专业）
- 用各自专业视角加权，但不设置审查边界
- "Lens, Not Boundary" — 专业是透镜，不是围墙

### 产出
每位评审员独立产出 JSON：
```json
{
  "vote": "approve|changes_requested|reject",
  "overall_score": 0-10,
  "dimensions": {
    "dim1": {"score": X, "evidence": "具体代码或文档引用"},
    "dim2": {"score": X, "evidence": "..."}
  },
  "findings": [
    {"finding": "具体问题描述", "severity": "blocker|major|minor", "evidence": "file:line", "dimension": "dim1"}
  ],
  "recommendations": ["可执行的修复建议"]
}
```

评分标准:
- 9-10: 卓越 — 超出预期
- 7-8: 良好 — 符合标准，小幅改进即可
- 4-6: 一般 — 可用但有明显缺陷
- 1-3: 不足 — 存在根本性问题

投票依据 overall_score: ≥7.0 → approve, 4.0-6.9 → changes_requested, <4.0 → reject

## Round 2: 交叉辩论

### 原则
- 所有审查者收到 **完整的 Round 1 结果**（包括其他人的打分和发现）
- 每个审查者必须：
  1. **挑战** 至少一个来自其他审查者的发现
  2. **识别** 跨视角冲突（如架构 vs 可实现性、产品需求 vs 工程可维护性）
  3. **承认** 自己遗漏的发现
  4. **辩护或让步** — 当自己的发现被挑战时

### 挑战规则

R1（架构）挑战路线：
- 挑战 R3: 某个工程捷径是否造成架构债务？
- 挑战 R2: 某个产品需求是否带来安全风险？

R2（产品）挑战路线：
- 挑战 R1: 架构过度设计是否损害用户体验？
- 挑战 R3: 代码质量取舍是否影响用户可见行为？

R3（工程）挑战路线：
- 挑战 R1: 架构设计是否实际可实现？
- 挑战 R2: 产品需求是否产生不可维护的代码？

### 产出
每位审查员产出辩论 JSON：
```json
{
  "challenges_to_R1": [{"finding": "R1的发现X", "challenge": "为什么不同意", "evidence": "..."}],
  "challenges_to_R2": [...],
  "challenges_to_R3": [...],
  "conflicts_identified": [
    {"perspectives": ["R1", "R3"], "issue": "架构 vs 工程权衡", "my_position": "...", "resolution_suggestion": "..."}
  ],
  "findings_i_missed": ["被R2或R3发现但我没注意到的"],
  "my_concessions": [{"finding": "我原来的发现", "concession": "为什么我错了", "score_impact": "-0.5"}],
  "my_defenses": [{"finding": "我原来的发现", "defense": "支持我立场的证据"}],
  "revised_vote": "approve|changes_requested|reject",
  "revised_overall_score": 0-10,
  "debate_summary": "1-2句：辩论揭示了什么独立审查没发现的？"
}
```

## Round 3: 合议裁决

Orchestrator 综合 Round 2 辩论结果：

### 共识区域（三个审查者一致同意）
- 最可靠的发现 — 三个不同视角都看到了

### 分歧区域（辩论后仍不一致）
- 真正的模糊地带 — 可能需要 CTO 介入
- 记录双方论点

### 冲突解决
- 记录每个冲突如何解决（或为什么未解决）

### 修订分数
使用辩论后 **Round 2 修订分数**（不是 Round 1 原始分）

## 投票与裁决规则

### 标准投票（Round 2 修订后）

| 票数分布 | 结果 |
|----------|------|
| ≥2 approve | ✅ PASS |
| ≥2 reject | ❌ REJECT |
| ≥2 changes_requested | 🔄 CHANGES REQUIRED |
| 1 approve + 1 reject + 1 changes_requested | ⚖️ DEADLOCK → CTO 仲裁 |

### CTO 仲裁（僵局时）

当 1:1:1 僵局发生时，CTO 作为最终仲裁者：

1. 阅读所有三个审查记录和辩论综合
2. 根据 gate 类型加权不同审查者的意见：
   - **DG1（设计）**: 偏向 R1（架构）— 设计阶段架构决策最重要
   - **DG2（核心开发）**: 偏向 R3（工程）— 代码质量最重要
   - **DG3（QA）**: 偏向 R3（工程）— 测试和性能最重要
   - **DG4（交付）**: 偏向 R2（产品）— 验收标准和UX最重要
3. 做出绑定裁决：PASS / REJECT / CHANGES_REQUIRED
4. 记录仲裁决策：偏向哪位审查者、为什么、接受什么风险
5. CTO 裁决为 **最终决定**，不可再辩论

### 重做流程（CHANGES REQUIRED）

最多 3 轮重做，使用辩论综合（而非原始发现）作为修复摘要：
1. 提取综合行动项
2. 根据 gate 类型调起负责 agent：
   - DG1 → Architect → Tech Lead
   - DG2 → Tech Lead → Senior Engineer
   - DG3 → Senior Engineer
   - DG4 → Tech Lead
3. Agent 接到：辩论综合中的具体修复项
4. 重跑完整三轮审查
5. 如果 3 轮后仍 CHANGES_REQUIRED → Phase Failed

### 阶段交接

当 gate 通过时，下一阶段 agent 收到综合辩论发现：
- "Gate <X> 通过。共识发现: <摘要>。需要关注的未解决分歧: <摘要>。"
- 这让后续团队知道之前评审中发现了什么问题

## 各 Gate 评审重点

### DG1 — 方案设计评审
**触发**: 技术方案设计完成，尚未编码
**材料**: PRD、架构评审报告、任务分解、设计稿、测试计划
**通过阈值**: ≥6.0/10
**偏向**: 偏 R1（架构）

### DG2 — 核心开发评审
**触发**: 核心功能开发完成，代码已通过 TL Code Review
**材料**: 核心代码、单元测试、设计还原截图、API文档
**通过阈值**: ≥7.0/10
**偏向**: 偏 R3（工程）

### DG3 — 质量保证评审
**触发**: QA测试完成，Bug修复结束
**材料**: 测试报告、Bug跟踪、性能报告、安全扫描报告
**通过阈值**: ≥7.5/10
**偏向**: 偏 R3（工程）

### DG4 — 交付评审
**触发**: 所有功能完成，准备交付
**材料**: 完整交付物、文档、部署方案、回滚方案
**通过阈值**: ≥8.0/10
**偏向**: 偏 R2（产品）

## 评审记录

每次评审的完整记录存储在 `projects/<name>/reviews/dg<n>.md`，包含：
- Round 1 三位审查者的独立评分和发现
- Round 2 辩论矩阵（挑战、冲突、让步、辩护）
- Round 3 综合裁决（共识、分歧、修订分数、CTO 仲裁如适用）
- 投票统计和最终决定
