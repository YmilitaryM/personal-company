# 工作流程

## 核心流程: 需求 → 交付

```
阶段1        阶段2        阶段3        阶段4        阶段5
需求分析  →  方案设计  →  开发实现  →  测试评审  →  交付验收
 2-3天       1-2天       5-10天       2-3天       1天

┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐
│  PM  │ → │CTO+TL│ → │  SE  │ → │评审团│ → │ 需求 │
│      │   │      │   │  DE  │   │  QA  │   │  方  │
└──────┘   └──────┘   └──────┘   └──────┘   └──────┘
              │                       │
        设计评审                 阶段评审门
        (CTO+TL)               (评审团3人)
```

## 各阶段详述

### 阶段1: 需求分析 (PM主导)
- **输入**: 需求方提出的原始需求
- **活动**: 需求访谈、竞品分析、用户故事编写
- **产出**: PRD文档、验收标准、用户故事地图
- **评审**: PM内部评审 → CTO确认

### 阶段2: 方案设计 (CTO+TL主导)
- **输入**: 已确认的PRD
- **活动**: 技术方案设计、架构设计、任务分解
- **产出**: TSD文档、WBS、迭代计划、设计稿
- **评审**: 设计评审会 (CTO+TL+设计师)
- **门禁**: 评审团阶段评审 ⚡

### 阶段3: 开发实现 (工程师主导)
- **输入**: 已通过评审的技术方案
- **活动**: 编码、单元测试、集成开发
- **产出**: 功能代码、测试用例、API文档
- **过程监管**: 每日站会、代码提交规范
- **门禁**: Code Review通过 + 测试覆盖率达标

### 阶段4: 测试评审 (评审团主导)
- **输入**: 开发完成的代码
- **活动**: 功能测试、集成测试、性能测试
- **产出**: 测试报告、Bug列表
- **门禁**: 评审团阶段评审 ⚡ (≥2/3赞成)

### 阶段5: 交付验收 (需求方)
- **输入**: 通过所有评审的交付物
- **活动**: 需求方验收、部署上线
- **产出**: 验收报告、部署清单
- **完成**: 需求方签字确认

## 评审门禁规则

### 触发节点
| 节点 | 时机 | 评审内容 | 必须 |
|------|------|----------|------|
| DG1 | 方案设计完成 | 技术方案、架构设计 | ✅ |
| DG2 | 核心功能开发完成 | 核心代码、设计还原 | ✅ |
| DG3 | 测试完成 | 测试报告、质量标准 | ✅ |
| DG4 | 交付前 | 完整交付物检查 | ✅ |

### 评审规则
- 每个节点3位评审员独立评审
- 每人投票: ✅通过 / ❌驳回 / 🔄修改后重审
- ≥2票✅ = 通过
- ≥2票❌ = 驳回，重新执行当前阶段
- ≥2票🔄 = 修改后重新提交评审（不退回阶段）

### 评审维度权重
| 维度 | DG1权重 | DG2权重 | DG3权重 | DG4权重 |
|------|---------|---------|---------|---------|
| 需求符合度 | 30% | 20% | 25% | 30% |
| 技术合理性 | 40% | 35% | 20% | 15% |
| 质量标准 | 15% | 35% | 40% | 35% |
| 风险评估 | 15% | 10% | 15% | 20% |

## 日常协作流程

### 每日站会 (Daily Standup)
- 各项目组同步进度
- 识别阻塞项
- 更新项目Dashboard

### 周迭代 (Weekly Sprint)
- 周一: Sprint Planning (TL主持)
- 周三: Mid-Sprint Check
- 周五: Sprint Review + Retrospective

### 异常处理
- 阻塞超过1天 → 上报TL
- 阻塞超过2天 → 上报CTO
- 技术分歧 → CTO最终决策
- 需求变更 → PM评估影响 → CTO审批
